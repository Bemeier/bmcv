# Virtual BMCV: shared-core sim → web, VCV later

**Status: phases 0-3 complete. Next: phase 4 (VCV Rack), when wanted.**

The web frontend has now been driven in headless Chromium: the panel builds
from the spec, tapping SAV selects AMP, dragging channel 0's encoder produces
output, holding QNT latches the mode, and 42 LEDs light with the firmware's own
colours. See open question 8 for an unresolved headless stability issue.

## Context

Goal: a virtual BMCV that runs the *real* firmware logic — first headless/scriptable, then
in a browser, later as a VCV Rack module. Same C core in all three, no forked DSP.

The UI-layer restructure (commits `77485eb`..`23de3c4`) did most of the hard part already:

- `HwState` carries **raw levels only**. Gestures derive once in `ui_input.c` from `curr->dt`.
  The old half-speed hold timer (`+=` onto a 2-deep ring buffer) is **gone**.
- `UiState` split out of `EngineState`; interaction state is now per-instance and contained.
- `tests/fixtures/fixture.c` already drives `engine_tick` from `button_state`/`encoder_delta`
  with `fixture_hold/press/release/encoder`. That *is* an input driver.

So this plan is smaller than it would have been. Three things remain:

1. `bmcv_state_update` (`Core/Src/Lib/bmcv.c:222-315`) still owns logic no host can reach:
   trigger_src fill, `Clock_Poll/Trigger/Reset` dispatch, slider CV summing, `input_state[]`
   fill, encoder delta from absolute position, 2s CRC autosave, error dismissal.
   `fixture.c` reimplements the `dirty` half and **skips the rest** — so today's tests cannot
   exercise clock sync, CV-modulated slider, or autosave at all.
2. Three globals block N instances in one process (VCV requirement).
3. Panel geometry lives only in the hardware repo's KiCad output; nothing consumes it.

Decisions taken: no Figma for now (generate a functional SVG from KiCad); sim core → web
first, VCV after.

**Panel geometry** — `../bmcv/production/positions.csv`, mm, y negative downward.
Transform to panel space (origin top-left of board): `x_p = x_csv`, `y_p = -y_csv`.
Board = 80.0 × 108.0 mm (Edge.Cuts x∈[30,110], y∈[30,138], placement origin (30,30)) = 16 HP.

Every WS2811 sits at the **identical coordinate** as the control it lights — verified:

```
U9 (7.5,38)   ← U1 encoder (7.5,38.3)      U17 (11.25,92.5) ← SW1 (11.25,92.5)
U13 (7.5,56)  ← U5 encoder (7.5,55.7)      U23 (5.5,103.5)  ← SW7 (5.5,103.5)
```

So LED→component is derivable from co-location alone, no netlist walk. Layout:

```
y   5-18   jacks:  J1-J4 (x 7/21) | J9-J12 (x 33/47) | J5-J8 (x 59/73)
y   38.3   encoders U1 U2 . . U3 U4      (x 7.5 25.5 | 54.5 72.5)
y   38/52/66  FN tactiles SW14/15/16     (x 40, centre column)
y   55.7   encoders U5 U6 . . U8 U7
y   80     slider RV13                   (x 40)
y   92.5   switch row A: SW1..SW6        (x 11.25 → 68.75, 11.5 pitch)
y   103.5  switch row B: SW7..SW13       (x 5.5 → 74.5, 11.5 pitch)
```

Role assignment is forced by counts + `hw_setup.c`: 6 ctrl buttons with LEDs → SW1-SW6;
3 ctrl buttons with `led == -1` → SW14-16; 7 scenes → SW7-SW13. Cross-check:
`quantizer_button_led_idx` must come out as a piano (white keys on row B, black keys on
row A with SW3 skipped). If it does, the whole mapping is confirmed.

**Scaling:** `ADC_10V 8192` (14-bit ±10 V in), `DAC_10V 32768` (16-bit ±10 V out).
`TRIG_THRESH 1024` / `TRIG_THRESH_LOW 800` (`dac_adc.h:7-8`) ≈ 1.25 V / 0.98 V.
Slider raw range 400..7661 (`state.h:11-12`).

**Timing:** engine is dt-driven (`channel.c` advances phase by `dt_s = hw_state->dt * US_TO_S`),
so it is correct at *any* tick rate. UX pass self-limits to 8 ms (`engine.c:UX_UPDATE_INTERVAL`).

## Phase 1 — finish the core seam

### 1a. Hoist the input layer

New **`Core/Inc/Lib/input_state.h`** + **`Core/Src/Lib/input_state.c`**, added to
`BMCV_CORE_SOURCES` in `cmake/core_sources.cmake`.

```c
// One tick of raw hardware input. Whoever owns the hardware fills this in:
// the driver layer on the STM32, the widget in VCV, the JS frontend via wasm.
typedef struct
{
  uint16_t slider_raw;              // pre-CV, SLIDER_MIN_VALUE..SLIDER_MAX_VALUE
  int16_t  cv_raw[N_INPUTS];        // ADC units, +/- ADC_10V
  uint8_t  cv_trig[N_INPUTS];       // rising edge latched since last tick
  uint8_t  button_down[N_BUTTONS];
  int16_t  encoder_pos[N_ENCODERS]; // free-running absolute
} InputSample;

typedef struct
{
  HwState  frames[STATE_RINGBUF_SIZE];
  uint8_t  idx;
  uint32_t last_autosave_us;
  int32_t  last_crc;
} InputState;

void    input_state_init(InputState*, UxState*, uint32_t now_us);
uint8_t input_state_update(InputState*, UxState*, const InputSample*, uint32_t now_us);

// Same hysteresis as dac_adc.c, so a host can edge-detect at its own sample rate.
uint8_t input_trig_step(int16_t cv, uint8_t* state);
```

`bmcv.c:222-315` moves in essentially verbatim, minus the peripheral reads.
`bmcv_state_update` shrinks to ~20 lines: fill an `InputSample` from `get_btn_state`/
`get_enc_state`/`get_adc`/`adc_read_trig_state`/`slider_adc_value`, call `input_state_update`.
Its signature and every other `bmcv_*` entry point are unchanged, so `Core/Src/main.c` and
the HAL callbacks are untouched.

**Why a plain struct, not a vtable:** the sample is a parameter, so N instances are free; no
indirection on the hot path (24 buttons + 8 encoders per tick); directly unit-testable; and it
matches the idiom `engine.h` already documents — caller fills state, core reads it. One idiom,
not two.

`preset_store`/`preset_load` are the exception, because the backing store genuinely differs
per instance (FRAM / patch JSON / localStorage) and it is a cold path:

```c
typedef struct {                       // new field on UxState
  int8_t (*store)(void* user, const EngineConfig*, int8_t slot);
  int8_t (*load) (void* user, EngineConfig*, int8_t slot);
  void* user;
} PresetIo;
```

`NULL` ⇒ store is a no-op, load returns 0 (the first-boot path). Touches `scene.c:99,104`,
`input_state.c`, `bmcv_init`. `tests/fakes/fake_drivers.c` loses two of its four stubs.

Also delete the `get_adc` call at `ui_render.c:127` in favour of
`state->hw_state->input_state[scene->id] / 4` — identical value, and it makes the MON LED path
testable for the first time.

### 1b. Reentrancy

Required now, not deferrable: VCV instantiates N modules in one process, and two instances
sharing a clock or an error latch is not shippable.

- `g_clk` → `ClockState clock;` field in `EngineState`; `Clock_*` take `ClockState*`.
  ~40 lines across `clock_sync.c`, `channel.c:337,352,354`, `bmcv.c`, `fixture.c`,
  `render_channel.c`, `test_clock_sync.c`, `test_channel.c`.
- `error_flags` → `uint8_t error_flags` in `EngineState`; `error_*` take `EngineState*`.
  ~10 lines. Call sites: `ui_render.c:189,197`, `scene.c:107`, `bmcv.c:103,311`.
- `static uint8_t min_value` / `input_mode_color` in `scene.c` → `static const`.
- `static UxSetup ux_setup` (`ux_setup.c:4`): leave, document. Write-once, deterministic from
  a `static const HwSetup`, all constructors on the main thread.

### 1c. Instance struct

New **`Core/Inc/Lib/instance.h`** + **`instance.c`**:

```c
typedef struct {
  const HwSetup* hw_setup;
  const UxSetup* ux_setup;
  EngineConfig config;
  EngineState  engine;
  UiState      ui;
  UxState      ux;
  InputState   input;
} BmcvInstance;

void    bmcv_instance_init(BmcvInstance*, uint32_t now_us);   // everything bmcv_init does minus peripherals
uint8_t bmcv_instance_tick(BmcvInstance*, const InputSample*, uint32_t now_us);
```

`bmcv.c` keeps one `static BmcvInstance` plus its DAC/LED flush loops.
`fixture.c` is rebuilt on `BmcvInstance` while `fixture.h`'s API stays byte-identical — that
is the proof the refactor is behaviour-preserving, since the other test suites don't change.
Fixture drops its private `prev_button_state`/`dirty` copy and gains clock + slider-CV +
autosave coverage for free.

## Phase 2 — sim library + headless CLI

New standalone CMake project `sim/CMakeLists.txt` (same pattern as `tests/CMakeLists.txt`,
includes `cmake/core_sources.cmake`).

- `bmcv_sim` — core + `sim/src/bmcv_sim.c` (instance wrapper, scope ring, preset backend)
  + `sim/src/sim_rt.c` (tick decimation, CV edge latch, volt↔raw scaling — **pure C, shared
  with the future VCV plugin**).
- `bmcv_sim_cli` — scriptable input timeline → CSV of outputs + LEDs + shift_state.

Exported C API (`sim/include/bmcv_sim.h`), designed so JS, VCV and tests all use it:

```c
BmcvSim* bmcv_sim_create(void);   void bmcv_sim_destroy(BmcvSim*);   void bmcv_sim_reset(BmcvSim*);

void bmcv_sim_set_button(BmcvSim*, uint8_t btn, uint8_t down);
void bmcv_sim_add_encoder(BmcvSim*, uint8_t enc, int16_t detents);
void bmcv_sim_set_slider01(BmcvSim*, float pos01);
void bmcv_sim_set_cv(BmcvSim*, uint8_t in, float volts);      // latches edges

void bmcv_sim_run(BmcvSim*, uint32_t dt_us, uint32_t n_ticks);

const float*   bmcv_sim_outputs_v(const BmcvSim*);   // 8 floats, volts
const uint8_t* bmcv_sim_leds_rgb(const BmcvSim*);    // 63 bytes
const float*   bmcv_sim_scope(const BmcvSim*);       // 8 * 4096 ring, volts
uint32_t       bmcv_sim_scope_head(const BmcvSim*);
uint8_t        bmcv_sim_shift_state(const BmcvSim*);
float          bmcv_sim_bpm(const BmcvSim*);
int32_t  bmcv_sim_config_size(void);
void     bmcv_sim_config_get(const BmcvSim*, void* dst);
int32_t  bmcv_sim_config_set(BmcvSim*, const void* src, int32_t len);
```

The scope ring lives **inside** the sim and is filled per tick, so a frontend makes ~4 calls
per frame regardless of tick rate. Single most important perf decision for the web build.

Value on its own: golden-file tests of whole UX flows (hold STA + tap scene, copy/clear,
save/recall) that have no coverage today.

`just sim`, `just sim-run`

## Phase 3 — web sim

- **Build:** `emcmake` on `sim/CMakeLists.txt` → `web/bmcv.js` + `web/bmcv.wasm`
  (`-sMODULARIZE -sEXPORT_ES6 -O3`).
- **Frontend:** `web/index.html` + `web/main.js`, no framework, no bundler. Renders the panel
  as SVG straight from `web/panel.json` — `<circle>` + rotating indicator for encoders,
  `<rect rx>` for switches with `fill` from the LED bytes, `<circle>` for jacks, `<rect>`
  slider. Pointer handlers map onto `set_button`/`add_encoder` via the spec's index fields.
  Encoders: vertical drag + wheel to turn, mousedown on the body = push (so press-and-turn
  works as on hardware). Hover overlay reads `roles`.
- **Tick loop:** `requestAnimationFrame` → `bmcv_sim_run(sim, 250, min(n, 400))` with
  `n = elapsed_us / 250`. Deterministic 4 kHz dt, decoupled from frame jitter, capped so a
  backgrounded tab doesn't produce a catch-up burst.
- **Visualisation** (no audio requirement): 8 stacked scope lanes on one `<canvas>` from the
  ring buffer, ±10 V grid; the 21 LEDs on the panel itself; BPM/beat-phase readout; per-channel
  FRQ/SHP/MOD/PHS/AMP/OFS inspector; 7 scene contribution bars. Clock/reset/CV inputs get UI
  generators (a BPM slider synthesising pulses into `set_cv`, as `render_channel.c:178` does).

`just wasm`, `just web`

## Phase 4 — VCV Rack (later, sketch only)

Deferred by decision. Recorded so phases 1-3 don't foreclose it:

- `vcv/` in this repo (`plugin.json`, `Makefile`, `src/`, `res/`), `BMCV_ROOT ?= ..` so the
  eventual move to a separate repo + submodule is a one-line change (the VCV Library requires
  the plugin at repo root).
- Reuses `sim/src/sim_rt.c` unchanged — ~95% of behaviour is already natively tested; what
  remains in `vcv/src/` is ~300 lines of widget marshalling.
- One aggregate `extern "C"` header rather than touching 30 firmware headers.
- 8 outputs, 4 inputs, 21 RGB lights → 63 slots, `VCVLightBezel<RedGreenBlueLight>` for the
  illuminated switches. Encoders: `configParam(-20000, 20000)` + snap, indicator drawn at
  `fmod(value, detents)` so it reads as endless; `encoder_pos` is already free-running and
  the delta is wrap-safe.
- Two-tier `process()`: CV edge latch per sample (`input_trig_step`), `bmcv_instance_tick`
  on a divider → 4 kHz (`divider = lround(sampleRate/4000)`, 12 @48 k; `dt_us` accumulated as
  an integer so there's no float drift).
- `dataToJson` serialises the 8 preset slots as base64 — the packed record already carries
  magic/version/length/crc and `config_validate()` tolerates junk, so patches survive
  firmware config changes for free.

`just vcv`, `just vcv-sdk` (fetch SDK — not installed on this machine).

## Verification

- **Regression floor:** `just test` (14 suites) green after every phase. Only `fixture.c`,
  `test_clock_sync.c` and `test_channel.c` may churn (1b/1c); the other 11 suites must be
  literally untouched.
- **New `tests/test_input_state.c`:** encoder delta incl. int16 wraparound; `INPUT_RESET`
  firing `Clock_Reset` + `reset_channel_phase` on all 8 channels; `INPUT_SLIDER` CV summing
  changing scene contribution; autosave firing once per 2 s per config change (counting
  `PresetIo`); `dirty` semantics; `input_trig_step` hysteresis with a 1-sample gate.
- **New `tests/test_panel_spec.c`:** the co-location invariant.
- **New `tests/test_sim_rt.c`:** divider arithmetic at 44.1/48/96/192 kHz; `now_us`
  accumulation with no drift over 10 min; volt↔raw round-trip at ±10 V and clamping beyond.
- **Multi-instance test:** two `BmcvInstance`s, different clocks, assert no cross-talk.
  This is the check that 1b actually landed.
- **Firmware:** `just configure && just build` after each phase — the ARM link is the proof
  nothing HAL-shaped leaked into core.
- **Web:** load `web/index.html`, drive a channel with an encoder, confirm the scope moves and
  the channel LED tracks output level; hold STA and confirm scene LEDs light per `ui_mode.c`.

## Open questions

1. ~~Output jack / channel crossing~~ **Resolved - there was never a crossing.**
   The apparent swap was a bug in the generator's DAC tracing: the two AD5754Rs
   are daisy-chained behind one shared SYNC, so the first command in each
   6-byte transfer ends up in the *second* device. Even buffer indices are U35,
   odd are U34. Corrected, channels 0-3 drive J1-J4 and 4-7 drive J5-J8, each
   in their encoders' reading order. `hw_setup.c` needed no change.
2. ~~Input jack <-> ADC index~~ **Resolved by the panel.** Static analysis
   cannot settle the `ADDR` phase, but only one of the two options numbers the
   input jacks 0-3 in the same reading order as everything else on the module
   (`A2/B2` in `adc_i[0..1]`). Recorded in `panel/overrides.json`. Still worth
   a one-minute confirmation on hardware: patch DC into one jack at a time and
   watch `HwState.input_state[]`.
3. **Slider travel.** The RV13 footprint gives a 73 x 16.8mm horizontal body;
   `overrides.json` infers a 60mm wiper stroke from that. Measure to confirm.
4. **Control rate for the sim.** 4kHz is an estimate. The firmware already
   computes `dac_fps`/`engine_fps` (`bmcv.c`); reading those off hardware would
   let the sim match the module's real update rate.
5. **LED colour fidelity.** `led_fb.c`'s integer HSV->RGB drives real WS2812s;
   SVG fills are linear. A gamma/glow pass is needed for the sim to *look*
   right. Cosmetic, but it is the first thing anyone judges.
6. **`uint32_t` us time wraps every ~71.6 min.** Deltas are wrap-safe, but
   `engine.c` uses `now_us % FAST_BLINK_PERIOD`, so a long-lived instance gets
   one blink hiccup per wrap. Harmless - worth a test so nobody "fixes" it.
7. **MIDI is out of scope** for the sim.
8. ~~Headless renderer dies intermittently~~ **Resolved - it was a real bug,
   not the environment.** `bmcv_sim_run` took an unsigned `n_ticks` and the
   frontend could hand it a negative one when rAF's frame timestamp preceded
   the `performance.now()` captured just before scheduling. -20 became ~4.29
   billion ticks and wedged the main thread. Every earlier observation fits:
   only with the engine in the loop, unaffected by `-O0`, invisible to
   SAFE_HEAP (not a memory error, just an enormous loop), and no JS error
   because nothing threw. Fixed on both sides and covered by `web/smoke.mjs`.
   The lesson: "flaky only in headless" was the wrong conclusion to draw from
   an intermittent hang.
